# Database Migrations

Until this was fixed, schema changes relied entirely on TypeORM's
`synchronize: true`, which is explicitly disabled in production
(`NODE_ENV=production` in `app.module.ts`) — meaning **production had no
schema-management story at all.** The first real schema change (a new
column, a new index) would have had nowhere to go. `synchronize` is now
`false` unconditionally, in every environment — dev, test, and prod all use
the same mechanism, specifically so dev/test can't silently diverge from how
prod actually behaves.

## The workflow

```bash
npm run migration:generate -- src/database/migrations/DescriptiveName  # diff entities vs DB, write SQL
npm run migration:run                                                  # apply pending migrations
npm run migration:revert                                               # roll back the most recent one
```

These read connection settings from real environment variables (or
`.env`/`.env.local`, same as the app) — `DB_MASTER_HOST`, `DB_MASTER_PORT`,
`DB_USERNAME`, `DB_PASSWORD`, `DB_NAME`. They always target the **master**
only; migrations must never run against a replica.

`src/database/data-source.ts` is a plain TypeORM `DataSource`, deliberately
separate from `app.module.ts`'s `TypeOrmModule.forRootAsync()` — the CLI
needs something it can import directly without booting Nest's DI container.
It lists the same entities the app uses, so `migration:generate` is always
diffing against the real, current entity definitions — there's no separate
schema description to keep in sync by hand.

**A real gotcha, hit twice building this project**: "the same entities the
app uses" means *listed in both places* — `app.module.ts`'s
`TypeOrmModule.forRootAsync()` entities array, **and**
`data-source.ts`'s. They're two separate arrays, not one shared constant,
because `data-source.ts` can't import from `app.module.ts` (it would pull
in the whole Nest DI graph just to run a CLI command). A new entity file
that's registered in `app.module.ts` (so the running app can read/write
it) but forgotten in `data-source.ts` doesn't error anywhere obvious —
`migration:generate` simply doesn't see the new table at all and reports
either no changes, or changes for everything *except* the new entity.
This happened twice in the same session (`ReserveHoldEntity`, then
`SubscriptionEntity`) — both times the fix was remembering to add the
`import` + array entry to `data-source.ts` too. **Checklist for a new
entity**: add it to `TypeOrmModule.forFeature([...])` in its owning
module, `app.module.ts`'s `entities:` array, *and* `data-source.ts`'s
`entities:` array — three places, not two.

## Where migrations run automatically

- **Docker image** (`Dockerfile`): the production `CMD` runs
  `node ./node_modules/typeorm/cli.js -d dist/database/data-source.js
  migration:run` before `exec node dist/main.js`. This is the actual "deploy
  step that runs migrations before the new app version starts serving
  traffic" that Tier 1 of `DEV_README.md` used to list as missing.
- **E2E tests** (`npm run test:e2e`): a `pretest:e2e` npm script (npm's
  standard pre-hook convention — runs automatically before `test:e2e`) runs
  `migration:run` against whatever `test/setup-env.ts` configures, so the
  e2e suite always exercises the real migration-created schema, never a
  synchronized one.
- **Local dev** (`npm run start:dev`): **not** automatic, deliberately —
  run `npm run migration:run` by hand after pulling a change that adds a new
  migration. Auto-running on every watch-mode restart would mean a failed
  DB connection breaks the dev loop instead of just the one command that
  needs it.

## How the baseline migration was produced

The initial migration (`src/database/migrations/*-InitialSchema.ts`) was
**not** hand-written — it was generated by running `migration:generate`
against a genuinely empty database (freshly initialized master, no prior
`synchronize` runs, no leftover tables), so it's provably exactly what the
entities describe, not a manually-transcribed approximation. After applying
it, running `migration:generate` again against the now-migrated database
produced "No changes in database schema were found" — confirming there's no
drift between the migration and the entities it was generated from.

## A bug this surfaced: `scripts/postgres/init-master.sql`

Generating that baseline migration required a truly fresh Postgres volume,
which is what actually exposed a real, previously-undiscovered bug: the
init script's `GRANT REPLICATION SLAVE ON DATABASE omniswitch_payments TO
replicator;` line is **MySQL syntax** — PostgreSQL has no `GRANT ... SLAVE`
form (replication access is granted entirely via the `REPLICATION` role
attribute in `CREATE ROLE`, which the script already did one statement
earlier). On every fresh cluster init, this line aborted the whole
`01-init.sql` script with a syntax error partway through, which in turn
meant `02-init-hba.sh` (see
[`infra-verification-status.md`](./infra-verification-status.md)) never got
a chance to run either — one broken SQL statement was silently taking out
an unrelated script later in the same init sequence.

The invalid line has been removed (the role's `REPLICATION` attribute was
already sufficient). While fixing this, `init-master.sql`'s `CREATE
TABLE`/`CREATE INDEX`/`CREATE TRIGGER` statements were also deleted
entirely — they defined a `payments` table that had drifted from
`PaymentEntity` for a long time (missing `merchant_id`, `psp_raw_response`
vs. the entity's actual column set, etc.) and were never really the schema
in effect; `synchronize: true` silently reconciled the difference every
time the app booted. Now that migrations own the schema, that file would
actively conflict with them instead of just being redundant, so
`init-master.sql` is now cluster-level setup only (the `replicator` role,
the `pg_stat_statements` extension) — no application tables.

## Verification

- Baseline migration generated against a genuinely empty DB; re-running
  `migration:generate` afterward reported no drift (see above).
- Full stack brought up from **entirely fresh volumes** (`docker compose
  down -v` then `up`), confirmed zero tables existed before migrations ran,
  then `npm run test:e2e` — whose `pretest:e2e` hook runs `migration:run`
  automatically — passed 33/33 against the migration-created schema.
- The exact production command (`node ./node_modules/typeorm/cli.js -d
  dist/database/data-source.js migration:run`) was run directly against
  compiled output (`nest build`'s `dist/`), not just the `ts-node` dev path,
  and correctly reported "No migrations are pending" against the
  already-migrated database — confirming the Dockerfile's `CMD` will work
  as written.
- **Not yet verified**: an actual `docker build` + container run of the
  production image exercising this `CMD` end to end (only the underlying
  command was verified directly, not the full image build/run). Tracked in
  [`infra-verification-status.md`](./infra-verification-status.md).
